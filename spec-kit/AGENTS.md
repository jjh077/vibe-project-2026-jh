# Part 1. UI/UX Designer Spec-Kit

# UI/UX Designer Spec-Kit

> 목적: 바이브 코딩 및 AI 에이전트가 사이트의 정보 구조, 시각 디자인, 반응형 레이아웃, 인터랙션, 접근성을 일관되게 설계·구현하도록 돕는 실무 기준.
>
> 적용 범위: HTML5, CSS3, JavaScript 기반 웹사이트. 프레임워크 사용 여부와 관계없이 적용할 수 있으며, 실제 프로젝트의 기술 스택과 기존 코드 구조를 우선한다.

---

## 1. 기본 원칙

1. **요구사항 우선**: 디자인 토큰이나 예시값을 사이트의 브랜드 가이드보다 우선하지 않는다. 브랜드 가이드, 제공된 시안, 기존 사이트, 사용자 요구사항이 있으면 이를 먼저 분석한다.
2. **일관성**: 색상, 타이포그래피, 간격, 모서리, 그림자, 컴포넌트 상태를 공통 규칙으로 관리한다.
3. **사용성 우선**: 시각적 완성도뿐 아니라 정보 우선순위, 가독성, 탐색 편의성, 입력 편의성을 고려한다.
4. **반응형 우선**: 특정 기기 화면을 축소하는 방식이 아니라 콘텐츠가 자연스럽게 재배치되도록 설계한다.
5. **필요한 만큼만 설계**: 요구사항에 없는 복잡한 애니메이션, 컴포넌트, 장식 요소를 임의로 추가하지 않는다.
6. **기존 프로젝트 존중**: 기존 디자인 시스템과 구현 방식이 있다면 먼저 파악하고, 합리적인 이유 없이 전면 교체하지 않는다.

## 2. 디자인 시스템 및 토큰

### 2.1 토큰 관리 원칙

- 색상, 글꼴, 글자 크기, 간격, 테두리, 그림자, 모션 값은 가능한 한 CSS Custom Properties로 관리한다.
- 컴포넌트에서 반복되는 값을 임의의 하드코딩 값으로 계속 추가하지 않는다.
- 아래 값은 **초기 기본값 예시**이며, 프로젝트의 브랜드 컬러·시안·콘텐츠에 맞게 조정한다.
- 의미 기반 토큰(`--color-text-primary`)을 우선 사용하고, 원시 팔레트 값은 토큰 정의 영역에서 관리한다.
- 한 번 정한 토큰의 이름과 의미를 프로젝트 전체에서 일관되게 사용한다.

## 3. 레이아웃 및 반응형 규칙

### 3.1 공통 레이아웃

- 전역 `box-sizing: border-box`를 적용한다.
- 주요 콘텐츠는 일관된 컨테이너 폭과 좌우 여백을 사용한다.
- 컨테이너 중앙 정렬이 필요한 경우 `max-width`와 좌우 `auto` margin을 사용한다.
- `overflow-x: hidden`을 전역 또는 모든 부모 요소에 무조건 적용하지 않는다. 가로 넘침의 원인을 찾아 수정하고, 캐러셀 등 의도된 가로 스크롤은 유지한다.
- 고정 헤더·푸터·플로팅 버튼은 콘텐츠를 가리지 않는지 확인하고, 필요한 경우 스크롤 여백을 제공한다.
- 이미지와 미디어는 컨테이너를 벗어나지 않도록 크기와 비율을 관리한다.

```css
*,
*::before,
*::after {
  box-sizing: border-box;
}

html {
  scroll-behavior: smooth;
}

body {
  margin: 0;
  min-width: 320px;
  font-family: var(--font-family-base);
  color: var(--color-text-primary);
  background: var(--color-bg);
}

img,
svg,
video {
  max-width: 100%;
}

.container {
  width: min(100% - (var(--page-gutter) * 2), var(--container-max));
  margin-inline: auto;
}

@media (prefers-reduced-motion: reduce) {
  html {
    scroll-behavior: auto;
  }

  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

### 3.2 Breakpoint 가이드

브레이크포인트는 기기 이름에 고정하기보다 콘텐츠가 더 이상 자연스럽게 배치되지 않는 지점을 기준으로 선택한다. 다음 값은 시작점 예시다.

- Small: `0–639px` — 모바일 기본 단일 열, 필요 시 작은 카드 그리드
- Medium: `640–1023px` — 태블릿 및 좁은 창, 2열 중심
- Large: `1024–1279px` — 데스크톱 레이아웃
- Extra Large: `1280px 이상` — 넓은 화면, 최대 콘텐츠 폭 제한

모바일 우선으로 기본 스타일을 작성하고 `min-width` 미디어쿼리로 확장한다. 카드 열 수, 내비게이션 표시 방식, 여백은 실제 콘텐츠와 시안에 따라 조정한다. 320px 너비에서도 핵심 기능이 잘리지 않는지 확인한다.

### 3.3 반응형 검증

최소한 다음 화면 폭에서 확인한다.

- 320px / 360px / 390px
- 768px
- 1024px
- 1280px / 1440px

검증 항목: 가로 스크롤, 텍스트 잘림, 이미지 비율, 카드 열 수, 메뉴 전환, 버튼 터치 영역, 고정 요소의 콘텐츠 가림.

## 4. 타이포그래피 및 콘텐츠

- 제목과 본문 사이에 명확한 위계가 있어야 한다.
- 본문은 충분한 글자 크기와 줄 간격을 확보하고, 한 줄 길이가 지나치게 길어지지 않게 한다.
- 긴 제목이나 실제 운영 콘텐츠가 들어와도 레이아웃이 깨지지 않도록 한다.
- 텍스트를 이미지로 대체하지 않는다. 꼭 필요한 경우를 제외하면 실제 텍스트와 시맨틱 마크업을 사용한다.
- 숫자, 가격, 날짜, 단위 등은 콘텐츠 성격에 맞게 정렬과 표기 형식을 통일한다.

## 5. 컴포넌트 및 인터랙션

### 5.1 공통 상태

인터랙티브 컴포넌트는 해당 요소에 필요한 상태를 구현한다. 모든 요소에 모든 상태를 기계적으로 적용하지 않는다.

- Default: 기본 상태
- Hover: 마우스 호버가 가능한 환경에서만 제공
- Focus-visible: 키보드 탐색 시 식별 가능한 포커스 표시
- Active/Pressed: 클릭 또는 누름에 대한 피드백
- Disabled: 사용 불가 상태와 이유가 시각적으로 구분되는 상태
- Loading: 비동기 처리 중인 경우
- Error/Success: 입력 및 처리 결과를 알려야 하는 경우
- Empty: 목록이나 검색 결과가 없는 경우

```css
:where(button, a, input, select, textarea, [tabindex]:not([tabindex="-1"])):focus-visible {
  outline: 2px solid var(--color-focus);
  outline-offset: 2px;
}

@media (hover: hover) and (pointer: fine) {
  .button:hover {
    /* 프로젝트 토큰에 맞는 hover 스타일 */
  }
}

.button:active {
  /* 눌림 피드백은 과도하지 않게 적용 */
}

.button:disabled,
.button[aria-disabled="true"] {
  cursor: not-allowed;
  opacity: 0.55;
}
```

- `pointer-events: none`을 disabled 처리의 유일한 수단으로 사용하지 않는다. 실제 `<button disabled>` 등 의미에 맞는 HTML 속성도 함께 사용한다.
- 링크는 이동, 버튼은 동작에 사용한다.
- 메뉴, 모달, 탭, 아코디언, 드롭다운 등은 열림/닫힘, 선택, 포커스 이동, 바깥 클릭 및 Escape 처리 등 필요한 동작을 명확히 정의한다.
- 터치 환경에서는 hover만으로 중요한 정보나 기능을 제공하지 않는다.

## 6. 접근성(A11y)

목표 기준은 WCAG 2.2 AA를 참고한다. 프로젝트의 법적·서비스상 요구사항이 더 엄격하면 해당 기준을 우선한다.

1. 일반 텍스트 대비는 최소 4.5:1, 큰 텍스트는 최소 3:1을 확보한다.
2. 의미가 있는 UI 구성요소 및 그래픽의 대비는 관련 WCAG 기준을 확인한다. 장식용 아이콘까지 일률적으로 판단하지 않는다.
3. 색상만으로 오류, 선택, 상태를 전달하지 않는다.
4. 아이콘 단독 버튼에는 목적을 설명하는 접근 가능한 이름을 제공한다(`aria-label` 등).
5. 이미지에는 목적에 맞는 대체 텍스트를 제공한다. 장식 이미지는 빈 alt(`alt=""`)를 사용한다.
6. 폼 입력에는 연결된 `<label>`을 제공하고, 오류 메시지를 해당 입력과 연결한다.
7. 키보드만으로 모든 주요 기능을 사용할 수 있어야 하며 포커스 순서가 논리적이어야 한다.
8. 모달이 열리면 포커스를 내부로 이동시키고, 닫힐 때 호출 요소로 돌려보낸다. 필요한 경우 포커스 트랩을 구현한다.
9. 제목 태그는 문서 구조에 맞게 사용하고, 랜드마크(`<header>`, `<nav>`, `<main>`, `<footer>`)를 적절히 구성한다.
10. 자동 재생, 깜박임, 과도한 모션을 피하고 `prefers-reduced-motion`을 존중한다.
11. 터치 타깃은 가능하면 44×44 CSS px 이상을 권장한다. 공간 제약이 있는 경우 WCAG 기준과 인접 타깃 간격을 함께 확인한다.

## 7. 이미지 및 미디어

- 실제 제공된 이미지와 브랜드 에셋을 우선 사용한다. 임의로 다른 브랜드 이미지나 출처가 불명확한 이미지를 사용하지 않는다.
- 이미지 비율이 중요하면 `aspect-ratio`와 `object-fit`을 명시한다.
- 콘텐츠 이미지와 장식 이미지를 구분해 alt를 작성한다.
- 지연 로딩(`loading="lazy"`)은 초기 화면 밖의 이미지에 적용하고, 주요 LCP 이미지에는 무조건 적용하지 않는다.
- 이미지가 없거나 로드에 실패하는 경우 레이아웃이 무너지지 않도록 대체 상태를 마련한다.

## 8. 디자인 완료 체크리스트

- [ ] 제공된 시안·브랜드 가이드·요구사항을 우선 반영했는가?
- [ ] 색상·타이포그래피·간격·컴포넌트 규칙이 일관적인가?
- [ ] 모바일·태블릿·데스크톱에서 콘텐츠가 자연스럽게 재배치되는가?
- [ ] 가로 넘침, 잘림, 겹침, 이미지 왜곡이 없는가?
- [ ] 버튼·링크·폼·메뉴의 상태와 피드백이 명확한가?
- [ ] 키보드 포커스와 접근성 이름이 제공되는가?
- [ ] 대비, 대체 텍스트, 폼 레이블, 모션 감소를 확인했는가?
- [ ] 로딩·빈 화면·오류 등 필요한 상태가 설계되어 있는가?
- [ ] 불필요한 장식이나 요구사항에 없는 기능을 추가하지 않았는가?

## 9. 실제 사이트 소스 분석 기반 추가 기준 (Daycat / 그루밍데이 사례)

> 분석 대상: 제공된 `그루밍데이 고양이 _ 데이캣.html` 및 동봉 CSS 파일.
> 주의: 최초 제공 ZIP에는 핵심 최적화 파일이 포함되지 않았으나, 이후 `optimizer.php`, `optimizer_user.php` 및 관련 번들이 별도로 추가 업로드되었다. 추가 파일에서 확인된 디자인 토큰과 브레이크포인트는 문서 마지막의 부록을 함께 참조한다. 최종 적용값은 CSS 선언 순서와 실제 렌더링 결과로 검증한다.

### 9.1 페이지 정보 구조 및 섹션 순서

분석된 메인 페이지는 다음 순서를 기준으로 구성한다. 동일한 구조를 재현해야 할 때 섹션을 임의로 합치거나 순서를 바꾸지 않는다.

1. 사이트 헤더: 로고/브랜드 영역, 카테고리 내비게이션, 커뮤니티 링크, 회원·마이페이지 기능, 언어 선택, 검색
2. 메인 비주얼: 메인 슬라이드 배너
3. 브랜드 소개 영역: 시그니처 문구 및 브랜드 메시지
4. 베스트 상품: 상품 카드 목록과 가격/상품 정보
5. 포토 리뷰: 고객 리뷰 및 리뷰 이미지
6. 브랜드 콘텐츠 1: 코비·베리 앨범/스토리 콘텐츠
7. 브랜드 콘텐츠 2: 신규 영상/이야기 콘텐츠
8. YouTube Shorts: 세로형 짧은 영상 콘텐츠
9. Instagram: 소셜 채널 연결 영역
10. 푸터: 사업자 정보, 고객센터, 운영시간, 약관 및 정책 링크

### 9.2 헤더 및 탐색 경험

- 데스크톱 헤더와 모바일용 메뉴/검색 패널이 별도 DOM 또는 별도 표시 상태로 구성될 수 있음을 고려한다. 화면 폭이 줄어든다고 데스크톱 메뉴를 단순 축소하지 않는다.
- 모바일에서는 메뉴 열기/닫기, 카테고리 펼침, 검색 패널 표시/닫기 동작을 별도로 정의한다.
- 메뉴 버튼에는 `aria-expanded`, `aria-controls`를 적용하고, 패널이 닫힌 상태에서는 포커스 이동 및 키보드 탐색 대상에서 제외한다.
- 검색 입력, 최근 검색어, 인기 검색어 등 검색 UI가 존재한다면 빈 상태와 검색 결과 상태를 구분한다.
- 회원/마이페이지/장바구니/관심상품 등 계정 관련 링크는 로그인 상태에 따라 달라질 수 있으므로 정적 목업과 실제 계정 연동 상태를 구분한다.

### 9.3 상품 및 콘텐츠 컴포넌트

- 상품 카드는 대표 이미지, 상품명, 가격, 할인/판매 상태, 옵션 또는 구매 관련 액션 등 실제 데이터 필드를 기준으로 구성한다.
- 상품 이미지의 비율과 카드 열 수는 제공된 화면 또는 실제 CSS를 확인해 결정한다. 임의의 정사각형 이미지로 통일하지 않는다.
- 리뷰는 별도 콘텐츠 유형으로 취급하며 리뷰 이미지, 본문 요약, 평점, 작성자/작성일, 더보기/접기 등 확인된 정보를 구분한다.
- 브랜드 스토리·영상·숏폼·SNS 영역은 상품 카드와 동일한 컴포넌트로 억지로 통합하지 않는다. 콘텐츠 유형에 맞는 이미지/영상 비율과 제목 구조를 유지한다.
- 외부 영상이나 SNS 임베드는 로드 실패 시에도 섹션 높이와 주변 레이아웃이 무너지지 않도록 대체 상태를 마련한다.

### 9.4 시각 스타일 및 폰트

- 제공된 CSS에서 Pretendard 계열 폰트 선언과 Xeicon 아이콘 폰트 사용을 확인했다. 유사 사이트 재현 시 제공된 폰트 파일/선언을 우선 검토하되, 실제 적용 위치와 굵기는 핵심 스타일시트에서 재확인한다.
- `froala_style_ec.min.css`는 에디터 콘텐츠 표시용 스타일일 수 있으므로 사이트 전체 디자인 토큰의 근거로 사용하지 않는다.
- `smart-popup.slick.css`는 Slick 계열 팝업/슬라이더 스타일에 해당할 수 있으므로 일반 콘텐츠 카드 스타일과 구분한다.
- 핵심 스타일시트가 누락된 경우 스크린샷이나 브라우저 렌더링을 통해 색상·간격·폰트 크기를 확인하기 전까지 임의의 수치로 확정하지 않는다.
- 아이콘 폰트가 사용된 사이트를 재현할 때 아이콘의 시각적 모양뿐 아니라 접근 가능한 이름과 대체 텍스트를 함께 제공한다.

### 9.5 반응형 및 모션

- HTML 내 `D1W`, `D1TMB` 등 디바이스 구분용 클래스와 모바일 메뉴 관련 DOM이 확인되었다. 이는 기기별 노출/구조 분기가 존재할 가능성을 보여주지만, 정확한 CSS 브레이크포인트는 제공 자료만으로 확인할 수 없다.
- 브레이크포인트는 기존 CSS 또는 실제 렌더링을 확인해 추출한다. `768px`, `1024px` 등을 근거 없이 기존 사이트의 실제 값이라고 기록하지 않는다.
- 메인 배너와 일부 콘텐츠에 Swiper 구조(`swiper-container`, `swiper-wrapper`, `swiper-slide`) 및 초기화 상태 클래스가 확인된다. 슬라이드 수, 자동재생, 전환 속도, 터치 동작, 페이지네이션/화살표 노출은 실제 설정을 확인해 재현한다.
- 팝업용 Slick 스타일시트도 포함되어 있으므로 Slick과 Swiper를 같은 슬라이더라고 가정하지 않는다.
- 자동재생 슬라이더에는 일시정지/재생 제어, 키보드 접근성, 모션 감소 설정을 고려한다.

### 9.6 디자인 분석 시 반드시 구분할 정보

- **확인됨**: HTML에 실제 존재하는 섹션, 문구, 링크, 클래스/ID, 콘텐츠 종류, 폰트 및 CSS 파일 선언
- **부분 확인**: 슬라이더/팝업 라이브러리의 사용 흔적, 디바이스 분기용 클래스, 동적 콘텐츠 구조
- **미확인**: 누락된 최적화 CSS에 들어 있는 실제 색상/간격/브레이크포인트, 동작 설정값, API 응답 및 서버 측 기능

미확인 항목은 디자이너의 추정값을 사실처럼 명세하지 말고, `추가 확인 필요`로 기록한다.

# Part 2. Frontend Developer Spec-Kit

# Frontend Developer Spec-Kit

> 목적: 바이브 코딩 및 AI 에이전트가 요구사항에 맞는 안정적이고 유지보수 가능한 웹사이트를 구현하도록 하는 개발 규칙.
>
> 적용 범위: HTML5, CSS3, Modern JavaScript 기반 웹 프로젝트. Vanilla JS를 기본 예시로 사용하지만, 기존 프로젝트의 프레임워크·빌드 도구·폴더 구조가 있으면 이를 우선한다.

---

## 1. 개발 기본 원칙

1. **기존 프로젝트 먼저 파악**: 코드를 수정하기 전에 파일 구조, 사용 기술, 실행 방법, 기존 디자인 시스템과 주요 기능을 확인한다.
2. **요구사항 우선**: 요청된 기능과 화면을 정확히 구현한다. 요구사항에 없는 기능이나 라이브러리를 임의로 추가하지 않는다.
3. **최소 복잡성**: 문제를 해결하는 가장 단순한 구조를 선택한다. 자체 프레임워크, 전역 상태 관리, 라우터, 추상 클래스는 실제 필요성이 있을 때만 도입한다.
4. **기존 코드 존중**: 동작 중인 코드를 이유 없이 전면 재작성하거나 파일 구조를 대규모로 변경하지 않는다.
5. **관심사 분리**: 화면 구조, 스타일, 데이터 처리, 비즈니스 로직을 가능한 범위에서 분리한다.
6. **명시적 실패 처리**: 로딩, 오류, 빈 데이터, 네트워크 실패 상황을 고려한다.
7. **검증 없는 완료 선언 금지**: 실행·빌드·테스트를 수행하지 못했다면 완료했다고 단정하지 말고 확인하지 못한 항목을 명시한다.

## 2. 작업 진행 프로토콜 (Vibe Coding)

각 작업은 다음 순서로 진행한다.

1. 요청과 수용 기준을 정리한다.
2. 관련 파일과 기존 구현을 확인한다.
3. 변경 범위를 정하고 필요한 경우 작업 계획을 짧게 제시한다.
4. 기존 규칙에 맞춰 최소한의 파일만 수정한다.
5. 구현 직후 문법·실행·화면·기능을 검증한다.
6. 발견한 오류를 수정하고 영향을 받는 기능을 재검증한다.
7. 변경 파일, 구현 내용, 테스트 결과, 남은 제한사항을 요약한다.

추가 규칙:
- 사용자가 제공한 디자인 이미지나 참고 사이트가 있으면 구조, 간격, 타이포그래피, 이미지 비율, 반응형 차이를 먼저 분석한다.
- 화면을 임의로 단순화하거나 섹션·콘텐츠를 누락하지 않는다.
- 실제 API나 백엔드가 없는 경우 임의의 성공 응답을 실제 연동처럼 표현하지 않는다. 필요한 경우 목업 데이터임을 명확히 구분한다.
- 작업 범위가 불명확하고 잘못된 선택의 영향이 큰 경우에만 확인 질문을 한다. 합리적으로 결정 가능한 세부사항은 일관된 기본값을 사용하고 기록한다.

## 3. 기술 스택 및 아키텍처

### 3.1 기술 스택 선택

- 기존 저장소에 프레임워크, 패키지 매니저, 빌드 도구가 있으면 이를 유지한다.
- 새 프로젝트는 요구사항과 배포 환경에 맞는 최소한의 스택을 선택한다.
- 정적 페이지 중심 사이트는 HTML/CSS/JavaScript만으로 충분할 수 있다.
- 복잡한 상호작용이나 데이터 흐름이 필요하다는 이유만으로 자체 프레임워크를 만들지 않는다.
- 새 라이브러리나 패키지를 추가하기 전 필요성, 번들 크기, 유지보수성, 보안 영향을 고려한다. 기존 의존성으로 해결할 수 있으면 새 패키지를 추가하지 않는다.

### 3.2 권장 디렉터리 예시

프로젝트 규모에 맞춰 필요한 폴더만 사용한다. 아래 구조를 무조건 강제하지 않는다.

```text
/
├── index.html
├── pages/                 # 별도 HTML 페이지가 필요한 경우
├── styles/
│   ├── variables.css
│   ├── reset.css
│   ├── global.css
│   └── components/
├── js/
│   ├── app.js
│   ├── components/        # 재사용할 UI 단위가 있을 때
│   ├── services/          # API 및 외부 데이터 처리
│   ├── utils/             # 순수 공통 함수
│   └── store/             # 공유 상태가 실제로 필요할 때
├── assets/
│   ├── images/
│   ├── icons/
│   └── fonts/
└── README.md
```

- 파일명과 export 방식은 프로젝트 전체에서 일관되게 유지한다.
- 한 파일에 무관한 기능을 과도하게 몰아넣지 않는다.
- 반대로 한두 줄짜리 함수까지 무조건 별도 파일로 분리하지 않는다.
- 라우팅은 다중 페이지 방식인지 SPA 방식인지 프로젝트 요구에 따라 결정한다. 단순한 다중 페이지 사이트에 클라이언트 라우터를 추가하지 않는다.

## 4. JavaScript 구현 규칙

### 4.1 모듈과 함수

- ES Module(`import`/`export`)을 사용하되 기존 실행 환경과 호환되는지 확인한다.
- 함수는 하나의 명확한 책임을 갖도록 작성한다.
- 전역 변수와 전역 함수 사용을 최소화한다.
- 상수는 `const`, 재할당이 필요한 변수는 `let`을 사용하고 `var`는 새 코드에서 사용하지 않는다.
- 비동기 작업은 `async/await`와 명시적 오류 처리를 우선한다.
- DOM 요소가 존재한다고 가정하지 말고 선택 결과와 실행 시점을 확인한다.

### 4.2 DOM 및 이벤트

- 이벤트 리스너는 해당 요소의 생명주기와 함께 관리한다.
- 반복 생성되는 목록에는 이벤트 위임을 사용할 수 있지만, 모든 이벤트를 무조건 위임하지 않는다.
- 이벤트 위임 시 `event.target`이 Element인지 확인한 뒤 `closest()`를 사용하고, 대상이 부모 영역 안에 있는지 확인한다.
- 이벤트 핸들러를 제거해야 하는 경우 동일한 함수 참조를 보관하거나 `AbortController`의 `signal`을 사용한다.
- `innerHTML`로 DOM을 교체하면 기존 자식 노드, 포커스, 입력값, 이벤트 연결이 사라질 수 있음을 고려한다.
- 작은 변경을 위해 전체 화면을 매번 재렌더링하지 않는다. 필요한 영역만 갱신한다.
- DOM을 만들 때 사용자 입력 문자열은 `textContent` 또는 안전한 DOM API를 우선 사용한다.

이벤트 위임 예시:

```javascript
const list = document.querySelector(".product-list");

list?.addEventListener("click", (event) => {
  if (!(event.target instanceof Element)) return;

  const button = event.target.closest("[data-action='add']");
  if (!button || !list.contains(button)) return;

  const productId = button.dataset.productId;
  if (!productId) return;

  addToCart(productId);
});
```

### 4.3 상태 관리

- 컴포넌트 내부에서만 쓰는 값은 로컬 상태로 관리한다.
- 여러 화면이나 컴포넌트가 공유하는 상태가 실제로 필요할 때만 공통 Store를 도입한다.
- 상태 변경 시 화면이 어떤 방식으로 갱신되는지 명확하게 유지한다.
- 상태 객체를 직접 변경할지 불변 업데이트를 사용할지 프로젝트 내에서 일관되게 정한다.
- `Proxy` 기반 반응형 시스템이나 자체 Pub/Sub 엔진은 필요성과 테스트 가능성이 확인된 경우에만 구현한다.
- 구독 기능이 있다면 반드시 해제 함수(unsubscribe)를 제공하고, 컴포넌트 종료 시 구독을 해제한다.
- `localStorage`에는 비밀번호, 인증 토큰 등 민감한 정보를 저장하지 않는다. 저장 데이터는 파싱 실패·만료·버전 변경 상황을 처리한다.

### 4.4 컴포넌트 생명주기

공통 Base Component 클래스를 모든 UI에 강제하지 않는다. 클래스나 별도 생명주기 관리가 실제로 필요한 경우 아래 원칙을 따른다.

- 초기화, 이벤트 등록, 렌더링, 정리 작업의 책임을 구분한다.
- `destroy()` 또는 동등한 정리 함수에서 이벤트 리스너, 타이머, Observer, Store 구독, 진행 중인 요청 등을 해제한다.
- `setInterval`, `setTimeout`, `requestAnimationFrame`, `IntersectionObserver`, `ResizeObserver` 등을 사용했다면 종료 시 정리한다.
- DOM을 교체한 뒤 이전 노드에 연결된 이벤트나 참조가 남지 않도록 한다.
- `AbortController`를 사용해 이벤트와 fetch 요청의 생명주기를 관리할 수 있다.

## 5. HTML 및 CSS 규칙

### 5.1 HTML

- 시맨틱 HTML 요소를 목적에 맞게 사용한다.
- 버튼 동작에는 `<button>`, 페이지 이동에는 `<a>`를 사용한다.
- 폼 입력에는 연결된 `<label>`을 제공한다.
- 이미지에는 목적에 맞는 `alt` 속성을 제공한다.
- 제목은 시각적 크기만을 위해 선택하지 않고 문서 구조에 맞는 계층을 사용한다.
- 필요한 경우 `lang`, `meta viewport`, 문서 제목, 설명 등 기본 메타 정보를 설정한다.

### 5.2 CSS

- 공통 디자인 값은 CSS Custom Properties로 관리한다.
- 클래스명은 역할과 의미를 드러내도록 작성한다.
- 과도한 선택자 중첩, 불필요한 `!important`, 인라인 스타일 남용을 피한다.
- 레이아웃은 Flexbox, Grid 등 목적에 맞는 CSS 기능을 사용한다.
- 모바일 우선으로 작성하고 실제 콘텐츠에 맞춰 미디어쿼리를 조정한다.
- `overflow-x: hidden`으로 문제를 숨기지 말고 넘침 원인을 해결한다.
- 고정 높이를 남용하지 않는다. 콘텐츠 길이와 글꼴 확대에도 레이아웃이 유지되어야 한다.
- 애니메이션은 목적이 있을 때만 적용하고 `prefers-reduced-motion`을 지원한다.

## 6. 보안 기준

### 6.1 XSS 및 DOM 삽입

- 사용자 입력, URL 파라미터, 외부 API 응답을 신뢰하지 않는다.
- 텍스트 삽입은 `textContent`, 입력값 설정은 `value`, 속성 설정은 적절한 DOM API를 우선한다.
- `innerHTML` 사용이 불가피한 경우 신뢰할 수 있는 정화(sanitization) 라이브러리를 사용하고 허용 태그·속성을 제한한다.
- 단순 HTML Escape 함수는 모든 상황에 통하는 범용 Sanitizer가 아니다. HTML 텍스트, 속성, URL, JavaScript 등 문맥마다 안전한 처리가 다르다.
- `href` 또는 `src`에 사용자 제공 URL을 넣을 때 허용 프로토콜을 검증하고 `javascript:` 등 위험한 스킴을 차단한다.
- 외부 링크를 새 창으로 열 때 필요한 경우 `rel="noopener noreferrer"`를 지정한다.

### 6.2 인증 및 비밀정보

- API 키, 비밀번호, 비밀 토큰을 프론트엔드 코드나 저장소에 하드코딩하지 않는다.
- 브라우저에 전달된 코드는 사용자가 확인할 수 있다고 가정한다.
- 인증·권한 검증은 서버에서도 수행해야 하며 UI에서 버튼을 숨기는 것만으로 권한을 보호했다고 판단하지 않는다.
- HTTPS 사용과 서버 측 입력 검증을 전제로 설계한다.

## 7. 성능 및 리소스 관리

- 최적화는 실제 병목이나 명확한 비용이 있는 곳에 적용한다.
- Scroll, Resize, 입력 이벤트에서 무거운 작업을 반복한다면 throttle/debounce를 고려한다.
- DOM을 반복 변경하는 작업은 묶어서 처리하되, `DocumentFragment`를 모든 상황에 의무적으로 사용하지 않는다.
- 이미지 크기와 포맷을 최적화하고, 초기 화면 밖의 이미지에 지연 로딩을 적용한다.
- 주요 콘텐츠 이미지의 로딩 우선순위를 불필요하게 낮추지 않는다.
- 불필요한 네트워크 요청과 중복 이벤트 등록을 방지한다.
- Observer, 타이머, 이벤트 리스너, 구독, 요청 등 사용한 리소스는 더 이상 필요하지 않을 때 해제한다.

## 8. 폼 및 비동기 처리

- 입력값은 클라이언트에서 사용자 편의를 위해 검증하되 서버에서도 반드시 검증한다.
- 오류 메시지는 어떤 항목이 왜 잘못되었는지 구체적으로 안내한다.
- 제출 중 중복 요청을 방지하고 로딩 상태를 표시한다.
- 성공·실패 결과를 사용자에게 명확히 알린다.
- 네트워크 오류, 빈 응답, 예상하지 못한 데이터 형식을 처리한다.
- fetch 사용 시 `response.ok`를 확인한다. fetch는 HTTP 오류 상태에서 자동으로 reject되지 않는다.

```javascript
async function fetchJson(url, options = {}) {
  const response = await fetch(url, options);

  if (!response.ok) {
    throw new Error(`요청 실패: ${response.status}`);
  }

  return response.json();
}
```

## 11. 실제 사이트 소스 분석 및 기존 플랫폼 보존 규칙

> 분석 대상: 제공된 Daycat / 그루밍데이 메인 HTML과 ZIP 내 CSS 파일.
> 분석 범위: 최초 ZIP에는 최적화 CSS가 없었으나, 이후 관련 최적화 CSS·JS 번들이 별도로 추가 업로드되었다. 확인된 라이브러리 버전과 디자인 토큰, 브레이크포인트는 문서 마지막의 부록에 정리한다. 페이지별 초기화 옵션과 실제 실행 흐름은 별도 확인이 필요하다.

### 11.1 구현 전 소스 인벤토리

기존 사이트 또는 참고 사이트의 소스를 제공받으면 코드를 수정하기 전에 다음을 확인한다.

- HTML의 주요 랜드마크와 페이지 섹션 순서
- 클래스/ID, `data-*` 속성, 폼 필드, 링크 목적지
- 연결된 CSS/JS 파일과 외부 CDN/서비스
- 폰트 및 아이콘 리소스
- 슬라이더, 팝업, 영상, 리뷰, 검색 등 동적 UI의 초기화 흔적
- 디바이스별 DOM 분기 및 CSS 미디어쿼리
- Cafe24 등 쇼핑몰 플랫폼의 모듈/앱이 생성하는 DOM과 데이터 바인딩

파일명만 보고 기능을 단정하지 말고, 실제 HTML 참조와 실행 코드를 함께 확인한다.

### 11.2 Cafe24 및 기존 플랫폼 마크업 보존

Daycat HTML에서는 Cafe24 계열 모듈 클래스(`xans-*`, `ec-*`)와 테마/확장 기능 클래스(`d1-*`)가 다수 확인되었다. 유사한 플랫폼 기반 프로젝트를 수정할 때 다음을 준수한다.

- `xans-*`, `ec-*`, `d1-*` 클래스, 기존 ID, `data-*` 속성은 역할을 확인하기 전 삭제·변경하지 않는다.
- 상품/게시판/회원 모듈이 사용하는 반복 구조와 서버 출력 마크업을 임의로 평탄화하거나 정적 HTML로 대체하지 않는다.
- 플랫폼이 요구하는 폼 name, action, input type, hidden field, 상품 식별자, 링크 URL을 보존한다.
- CSS를 정리할 때 플랫폼 스크립트가 참조하는 선택자와 동적 상태 클래스를 먼저 검색한다.
- 기존 DOM 구조를 바꾸는 경우 상품 목록, 장바구니, 검색, 회원 기능, 리뷰 등 연동 기능에 미치는 영향을 검증한다.
- 실제 플랫폼 연동이 없는 신규 구현에서는 Cafe24 모듈 클래스를 무의미하게 복제하지 않는다. 필요한 기능과 데이터 구조만 명확히 구현한다.

### 11.3 외부 라이브러리 및 의존성 관리

제공 소스에서는 jQuery 3.6.0, jQuery Migrate, YouTube IFrame API, Kakao SDK, Slick 계열 팝업 리소스, Swiper DOM 구조, Cafe24 및 분석/마케팅 관련 스크립트가 확인되었다. 실제 로딩 및 초기화 여부는 HTML과 스크립트 실행 상태를 함께 확인한다.

- 기존 라이브러리가 담당하는 기능을 확인한 뒤 중복 라이브러리를 추가한다.
- Swiper와 Slick은 별도 라이브러리/기능으로 취급하고, 실제 초기화 코드 및 설정을 확인한다.
- jQuery 기반 코드가 남아 있으면 의존 범위를 확인하기 전 jQuery를 제거하지 않는다.
- YouTube/Kakao 등 외부 SDK는 로드 실패, 차단, 네트워크 지연 상황을 고려한다.
- Facebook Pixel, Analytics, 광고/전환 추적 등은 기능 코드와 구분하고, 사용자 동의 및 개인정보 처리 요구사항을 확인한다.
- 외부 스크립트를 신규 프로젝트에 복사할 때 추적 코드나 제3자 SDK를 목적 확인 없이 포함하지 않는다.
- 외부 스크립트의 중복 로딩, 실행 순서, `async`/`defer`에 따른 초기화 경쟁 상태를 점검한다.

### 11.4 슬라이더·팝업·영상 기능

- 슬라이더는 HTML 클래스만으로 설정값을 추정하지 않는다. 초기화 코드에서 `slidesPerView`, `spaceBetween`, `loop`, `autoplay`, `speed`, `breakpoints`, pagination/navigation 설정을 확인한다.
- 모바일에서 터치 드래그와 페이지 스크롤이 충돌하지 않는지 확인한다.
- 자동재생을 사용하는 경우 일시정지 제어, 접근 가능한 버튼 이름, 모션 감소 설정을 제공한다.
- 팝업은 열기/닫기, 오늘 하루 보지 않기 등 저장 방식, Escape/바깥 클릭, 포커스 이동, 스크롤 잠금 동작을 분리해 구현한다.
- YouTube 임베드는 로딩 실패와 쿠키/외부 콘텐츠 차단 상태에 대한 대체 UI를 제공한다.

### 11.5 반응형 구현 기준

- `D1W`, `D1TMB` 등의 클래스가 존재한다는 사실만으로 정확한 화면 폭이나 브레이크포인트를 추정하지 않는다.
- 미디어쿼리는 제공된 CSS에서 실제 값을 추출하거나, 브라우저 렌더링을 여러 화면 폭으로 확인해 결정한다.
- 데스크톱 내비게이션과 모바일 메뉴가 별도 구조라면 각 구조의 접근성 상태와 이벤트를 독립적으로 관리한다.
- 모바일 메뉴는 열림/닫힘 상태, 본문 스크롤 잠금, 포커스 이동, Escape 닫기, 하위 메뉴 확장 상태를 정의한다.
- 모바일 검색 패널과 메뉴 패널이 동시에 열릴 수 있는지, 한 패널을 열면 다른 패널이 닫히는지 기존 동작을 확인한다.
- 고정 헤더/플로팅 퀵메뉴는 작은 화면에서 본문 및 주요 버튼을 가리지 않도록 한다.

### 11.6 누락된 리소스 및 불확실성 처리

- HTML에서 참조하지만 제공되지 않은 파일은 `누락 리소스`로 기록한다.
- 핵심 CSS가 누락된 경우 클래스명이나 사이트 캡처만으로 실제 CSS 선언을 만들어 사실처럼 기록하지 않는다.
- CSS가 없어서 확인할 수 없는 색상, 폰트 크기, 컨테이너 폭, 카드 간격, 브레이크포인트는 추가 자료 또는 브라우저 검증 대상으로 남긴다.
- 동적 데이터/API/서버 기능은 정적 HTML에 포함된 일부 샘플만으로 전체 동작을 추정하지 않는다.
- 분석 결과는 `확인됨 / 추정 / 미확인`으로 구분해 작업 계획과 결과 보고에 반영한다.

## 12. 기존 사이트 재현 작업 전용 체크리스트

- [ ] HTML의 섹션 순서와 주요 DOM 구조를 파악했는가?
- [ ] 플랫폼 모듈 클래스, ID, data 속성, 폼 필드를 확인했는가?
- [ ] CSS/JS 파일의 누락 및 외부 의존성을 정리했는가?
- [ ] 폰트와 아이콘 리소스를 확인했는가?
- [ ] 슬라이더/팝업/영상/검색/메뉴의 초기화 코드와 실제 동작을 확인했는가?
- [ ] 모바일 메뉴와 검색 UI의 상태 및 포커스 동작을 정의했는가?
- [ ] 미디어쿼리의 실제 값과 적용 범위를 확인했는가?
- [ ] 기존 쇼핑몰 기능 및 서버 연동을 깨뜨리지 않았는가?
- [ ] 외부 추적/마케팅 스크립트를 목적과 개인정보 관점에서 검토했는가?
- [ ] 확인하지 못한 항목을 완료한 것처럼 보고하지 않았는가?

## B. 디자인 시스템에서 확인된 값

`optimizer_user.php`의 CSS 변수에서 다음 값이 확인된다. 이는 해당 소스에 정의된 값이며, 실제 페이지에서 어떤 선언이 최종 적용되는지는 미디어쿼리와 CSS 선언 순서를 함께 고려해야 한다.

- 기본 글꼴: `Pretendard` 우선, 이후 맑은 고딕·돋움·시스템 산세리프 폴백
- 아이콘 폰트: `xeicon`
- 기본 텍스트 컬러: `#010101`
- 보조 텍스트 컬러: `#505050`, `#757575`, `#9a9a9a`
- 강조 컬러 변수: `--font-color-primary`, `--font-color-secondary`에 `#f5200fcc` 지정
- 성공/정보 계열 변수: `--font-color-success: #008bff`
- 포인트 컬러 변수: `--font-color-sp: #71442c`, 반전 텍스트 `#fff`
- 포인트 세일 컬러: `#f5200f`
- 최대 프레임 폭 변수: `1520px`, 보조 최대 폭 변수: `1360px`
- 썸네일·박스·팝업 라운드 변수: 각각 `3px`, `8px`, `5px`, `8px`; Shorts 라운드 변수는 `14px`
- 헤더 높이 변수: `100px`로 정의된 구간이 있으며, 별도 구간에서 `60px`로 재정의됨
- 콘텐츠 하단 여백·프레임 패딩도 화면 구간별로 다른 값이 정의됨

**주의:** `:root` 변수가 여러 구간에서 중복 정의되고 반응형 구간에서 재정의되므로, 위 값만 보고 모든 화면의 최종 적용값이라고 단정하지 않는다. 실제 적용값은 해당 요소의 계산된 스타일과 화면 너비에서 확인한다.

## C. 반응형 브레이크포인트

사이트 사용자 정의 CSS에서 반복적으로 확인되는 화면 구간은 다음과 같다.

- 모바일: `max-width: 767px`
- 태블릿: `min-width: 768px` 및 `max-width: 1024px`
- 데스크탑: `min-width: 1025px`
- 태블릿·모바일 공통 조정: `max-width: 1024px`

화면 구간별 표시 제어 클래스도 정의되어 있다. 예를 들어 `D1W*`, `D1T*`, `D1M*` 계열 클래스로 데스크탑·태블릿·모바일 전용 요소를 표시하거나 숨기는 규칙이 확인된다.

구현 지침:
1. 반응형 작업은 우선 위 브레이크포인트와 기존 표시 제어 클래스를 확인한다.
2. 모바일·태블릿·데스크탑 전용 콘텐츠가 이미 분리되어 있다면 무조건 하나의 DOM으로 합치지 않는다.
3. 새 브레이크포인트를 추가하기 전에 기존 미디어쿼리와 충돌하는지 확인한다.
4. HTML의 실제 구조, CSS의 선언 순서, 브라우저 계산 스타일을 함께 확인해 최종 레이아웃을 판단한다.

## D. 주요 컴포넌트 및 레이아웃 규칙

추가 CSS에서 다음과 같은 사이트 고유 구성 요소가 확인된다.

- 상품 리스트: `.d1-product-list`, `.ec-base-product` 및 상품 썸네일·상품명·가격·컬러 옵션 관련 규칙
- 포토 리뷰: `.d1-photoreview-*` 계열
- 브랜드 목록: `.brandlist` 및 검색/필터 영역
- 사이드 패널: `.d1sidebar`, `.mrightaside`
- 헤더: `#header`, `header .inner`, `.mheader` 및 고정 헤더 관련 규칙
- 푸터: `footer .inner`와 내부 영역의 반응형 재배치
- 메인 비주얼/배너: `.mainslide`, `.mainbwp001`
- 슬라이더 및 영상: `.swiper-container`, `.swiper-slide`, `data-youtube-id` 관련 규칙

따라서 새 화면을 구현할 때는 위 클래스와 유사한 기능을 중복 제작하기보다, 기존 컴포넌트의 역할과 스타일을 먼저 파악한다. 단, 클래스 이름만 같게 재사용하지 말고 실제 마크업 구조와 동작 의존성을 확인한다.

## E. JavaScript 및 외부 라이브러리 기준

확인된 버전 및 기능:
- Swiper `8.4.5`
- jQuery `3.6.0`
- Flatpickr `4.5.0`
- Cafe24 번역 처리 함수 및 다국어 전환 로직
- Cafe24 상품 더보기·상품 스와이프·폼 검증 등 쇼핑몰 공통 모듈

구현 지침:
1. 같은 라이브러리를 별도 버전으로 중복 로드하지 않는다.
2. 기존 Swiper 인스턴스와 컨테이너 구조를 확인한 뒤 슬라이더를 수정한다.
3. Cafe24의 상품 옵션, 장바구니, 회원, 다국어, 레이어 등 플랫폼 기능을 임의로 대체하지 않는다.
4. jQuery 기반 기존 기능이 남아 있다면, 일부 기능만을 위해 전체 코드를 무리하게 다른 방식으로 전환하지 않는다.
5. 최적화 번들만으로는 각 라이브러리의 실제 초기화 옵션이나 페이지별 실행 순서를 전부 확정할 수 없다. 필요한 경우 HTML의 호출부와 브라우저 실행 결과를 추가 확인한다.

## F. 분석 범위 및 남은 확인 사항

이번 업로드로 사이트 사용자 정의 CSS와 주요 공통 번들의 내용을 확인할 수 있게 되었지만, 다음 사항은 별도 검증이 필요하다.

- 최적화 번들 내부의 코드가 원래 어떤 개별 파일에서 왔는지에 대한 정확한 파일 단위 구분
- 각 슬라이더의 페이지별 초기화 옵션(자동 재생, 속도, 반복, 브레이크포인트 등)
- 메뉴·검색·사이드 패널·팝업의 실제 이벤트 흐름과 상태 전환
- 특정 화면 너비에서 최종 적용되는 CSS 값 및 요소별 계산 스타일
- 현재 서버에서 제공되는 리소스와 업로드된 파일 버전이 완전히 일치하는지 여부

AI 에이전트는 확인된 사실과 추정 사항을 구분해 보고하고, 미확인 설정을 임의로 만들어내지 않는다.
